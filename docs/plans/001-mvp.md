# MVP: Observe and Understand the Agent Fleet

## Status

Implemented

## Purpose

Create the first useful version of Agent Overlord: a self-contained terminal
application that continuously inventories agent-bearing tmux panes across the
local machine and configured SSH hosts, gives each pane a useful semantic
interpretation, shows control-system activity, and lets the user query or instruct
the control agents.

This MVP is intended to make the existing fleet legible and establish the
observe-understand loop on which later autonomous coordination will depend.

## User Outcome

From one interface, the user can:

- See all discovered agent sessions across configured hosts.
- Understand what each agent appears to be doing.
- Quickly identify agents awaiting input, stalled, failed, or disconnected.
- Observe a live stream of meaningful control-plane activity.
- Ask the control agents questions about the fleet.
- Give the control agents high-level instructions.

## Initial Interface

The initial interface is a Textual TUI with three primary panels.

### Agent Sessions Table

Each row represents an agent-bearing tmux pane. The initial columns are:

- Host.
- Tmux identity, displayed as `session:window.pane`.
- Semantic purpose.
- Harness.
- Model.
- Context size, usage, or availability.
- Current state, including whether the agent is awaiting input.

The implementation should preserve precise internal identity using host, tmux
server or socket, session, window, and pane identifiers even when the displayed
identity is abbreviated.

The initial state vocabulary should support at least:

- Active.
- Awaiting input.
- Idle.
- Stalled.
- Failed.
- Complete.
- Disconnected.
- Unknown.

Rows may be expanded to show supporting metadata and evidence, including recent
pane output, working directory, repository, branch, foreground command, last
observation time, and the reason for the current classification.

### Council Wall

The middle panel presents a live, tailing stream of meaningful control-plane and
control-agent events. It should make activity visible without displaying routine
polling noise.

Useful events include:

- Worker discovery.
- Changed purpose or state.
- Detected input or permission requests.
- Control-agent observations and discussion.
- Warnings, failures, and disconnections.
- Human instructions.
- Important memory updates.

The wall should support pausing visual follow, jumping to the latest event, and
basic filtering. Pausing the view must not pause observation or control agents.

### Council Chat

The bottom panel provides a conversational interface for querying and instructing
the control agents.

Initial examples include:

- What is blocked right now?
- What is this worker doing?
- Which agents are awaiting input?
- Why is this worker considered stalled?
- Focus on the documentation work.
- Remember that this repository is a work project.

Council answers should distinguish observed facts from semantic interpretations
and should link or refer to relevant workers and wall events where practical.

## Technical Direction

The MVP should be implemented as one self-contained Python 3.12+ application. It
does not require a separate daemon, HTTP API, browser frontend, JavaScript
toolchain, or network service between the interface and control plane.

The initial stack is:

- Python 3.12 or newer.
- `uv` for Python version selection, dependency management, locking, and command
  execution.
- A repository-local `.venv` virtual environment managed by `uv`.
- Textual for the terminal interface.
- `asyncio` for observation, controller, and UI concurrency.
- SQLite for durable operational state.
- Pydantic models for typed domain and event data.
- System `tmux` and `ssh` commands for local and remote observation and actions.

The repository should define its package and dependencies in `pyproject.toml` and
commit the generated `uv.lock`. Development and application commands should run
through `uv run`, while `uv sync` should reproducibly create or update `.venv`.
The virtual environment itself should not be committed.

Using the system SSH client lets the MVP honor the user's existing SSH
configuration, host-key policy, authentication agents, proxy configuration, and
connection multiplexing. A native Python SSH implementation is not required for
the MVP.

The reconciliation loop and Textual application may run in the same process and
event loop. The internal architecture should nevertheless keep domain logic,
transports, storage, and UI widgets separate. Textual widgets should consume typed
application services and events rather than execute tmux commands or SQL directly.

A possible package structure is:

```text
src/agent_overlord/
  app.py
  domain/
    workers.py
    events.py
    memories.py
    intents.py
  services/
    inventory.py
    classifier.py
    controllers.py
    arbiter.py
  transports/
    local_tmux.py
    ssh_tmux.py
  storage/
    sqlite.py
  ui/
    main.py
    sessions.py
    wall.py
    chat.py
```

This structure is a boundary guideline rather than a requirement to create every
module immediately. The core should expose application-level commands, queries,
and events so a separate daemon, API, or alternate interface could be added later
without being part of this MVP.

## Host and Tmux Discovery

The MVP should reuse or remain compatible with the existing host registry in
`tmux-watcher/config.yaml`. All currently known targets are reachable from
localhost either directly or over SSH.

Discovery should collect structured tmux metadata rather than parse presentation
output. Candidate metadata includes:

- Session, window, and pane identities and names.
- Tmux server or socket identity where applicable.
- Pane working directory, dimensions, foreground command, PID, title, activity,
  start command, and dead/alive state.
- Recent pane output.

Local and remote execution should use a common host/tmux transport abstraction.
The `tmux-watcher` project is reference material for `list-panes`, `capture-pane`,
`send-keys`, SSH connection handling, and host-scoped pane identity.

## Semantic Interpretation

The system should maintain a current semantic record for every discovered
agent-bearing pane. It should attempt to identify:

- Whether the pane contains an agent and which harness it uses.
- The model and context information when reliably available.
- The project, repository, or intent associated with the pane.
- A concise statement of the pane's purpose.
- Its current state.
- Whether it is asking for input and the apparent kind of request.
- Confidence, freshness, and supporting evidence for inferred values.

Deterministic classification should handle inexpensive, familiar cases. Semantic
model analysis should be reserved for changed or uncertain observations. Unknown
values are acceptable and should be represented honestly.

## Control Agents and Wall

The desired direction is more than one persistent control agent, mixing Claude
and Codex. Three control agents are a likely configuration so they can propose,
criticize, and reach consensus.

Possible roles include operator, auditor, and strategist. Exact role prompts,
model allocation, voting rules, and leadership behavior remain open design work.

The control agents need a shared wall-like communication channel inspired by
Goosetown's `gtwall`. The wall should retain append-only history, individual
reader progress, session or intent scoping, concurrent participation, and priority
for human messages. Consequential messages should support structured event data
even if the interface renders them as readable log lines.

Only one arbiter should eventually own actions against worker panes. Independent
control agents should not send competing input directly. Autonomous side effects
are deliberately outside the initial MVP acceptance criteria, but the event and
identity model should not prevent their later addition.

## Memory

Control agents should be able to retain durable, shared knowledge across process
restarts and context loss. Initial memory categories include episodic, semantic,
procedural, and user-preference memory.

Memories should be:

- Scoped to an appropriate global, host, project, intent, or worker context.
- Attributable to source observations, instructions, or events.
- Assigned confidence and freshness where relevant.
- Visible and explainable when they influence an answer.
- Correctable, supersedable, and removable by the user.
- Subordinate to explicit current instructions, `AGENTS.md`, and project ledger
  state.

The MVP should support at least explicit user-directed remembering and retrieval
through council chat. Automatic promotion, reinforcement, contradiction handling,
and memory curation may begin simply and evolve from observed use.

## Operational State

The control plane needs durable operational state separate from tmux. A local
SQLite database should hold observations, logical workers, events, control-agent
messages, memories, and interface state.

Tmux remains the live process and interaction substrate. Project ledgers remain
the durable source for project tasks, discoveries, decisions, and evidence. Git
remains the record of project changes. These responsibilities should not be
collapsed into one store.

## MVP Safety Boundary

The MVP should be observation-first.

It may:

- Connect to configured hosts.
- Read tmux metadata and pane output.
- Inspect relevant process and repository metadata.
- Maintain operational state and memories in the control-plane workspace.
- Run control agents to classify observations and answer user queries.

It should not initially:

- Automatically answer worker permission prompts.
- Type into worker panes without an explicit user instruction.
- Launch or terminate workers autonomously.
- Modify project repositories or ledgers on behalf of observed workers.
- Push, publish, install software, or change external systems.

Explicit user-initiated actions may be explored through the interface, but should
be visible, attributable, and verified.

## Non-Goals for This MVP

- Fully autonomous intent decomposition and completion.
- Automatic creation of tmux layouts, worktrees, ledgers, or worker sessions.
- Mature risk-based authority envelopes and approval consensus.
- Automatic recovery from every harness failure mode.
- A complete replacement for `tmux-watcher` as a manual pane interaction tool.
- Perfect model or context-size detection across every harness.
- Finalized long-term storage or deployment architecture.
- An HTTP API, separate background daemon, or browser-based frontend.

These remain expected future directions rather than discarded ideas.

## Acceptance Criteria

- [x] The system loads a host registry compatible with the existing
      `tmux-watcher` configuration.
- [x] The system runs as one Python application with a Textual terminal
      interface and requires no browser or separately managed API service.
- [x] `uv sync` creates a repository-local `.venv` from the committed
      `pyproject.toml` and `uv.lock`, and documented commands use `uv run`.
- [x] It continuously discovers tmux panes on the local and configured SSH hosts.
- [x] Agent-bearing panes appear as stable rows in the session table.
- [x] Each row shows host, tmux identity, purpose, harness, model, context, and
      current state, using unknown values where detection is not reliable.
- [x] Awaiting-input, stalled, failed, and disconnected workers are visually
      distinguishable.
- [x] Selecting a worker exposes recent output and the evidence behind its
      semantic classification.
- [x] Meaningful observations and control-agent activity appear in a tailing wall
      panel without routine polling noise.
- [x] The user can pause wall following, return to the latest event, and apply
      basic filters.
- [x] The user can query the council about fleet and worker state through chat.
- [x] The user can give the council a high-level instruction through chat and see
      it acknowledged on the wall.
- [x] The user can explicitly teach, retrieve, correct, and remove a shared
      control-agent memory.
- [x] Observed facts, inferred interpretations, wall events, and memories survive
      an application restart.
- [x] The system does not automatically send input to worker panes in the default
      MVP configuration.

## Implementation Evidence

- `uv sync --locked` reproducibly creates and validates the local environment
  from `pyproject.toml` and `uv.lock`.
- `uv run pytest -q` covers compatible configuration loading, structured tmux
  parsing, agent and state classification, SQLite restart persistence, independent
  wall-reader cursors, inventory transitions and disconnections, council queries,
  memory teaching/correction/removal, and the three-panel Textual interface.
- `uv run python -m compileall -q src tests` validates that all application and
  test modules compile.
- A live `--once` smoke test using `tmux-watcher/config.yaml` successfully
  inventoried the local and configured SSH hosts with no host errors. It found 12
  agent panes at the time of testing: eight Codex, four Claude, and three awaiting
  input.
- The transport layer exposes only read-only `list-panes` and `capture-pane`
  operations. There is no automatic pane-input path in the MVP.

## Open Questions

- How will Claude and Codex control agents run persistently and access the wall?
- Which harness metadata sources expose model and context information reliably?
- How should logical worker identity be reconciled after tmux restarts?
- What exact event schema and in-process wall interface should be used?
- Which semantic-memory retrieval approach is appropriate for the first
  implementation on top of SQLite?
- Which read-only repository and process inspections are acceptable by default?
- What is the smallest useful form of an explicit user-directed pane action?
